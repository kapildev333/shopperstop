A 304 only reaches this code if a request carries conditional headers; none of the admin client's calls do, and the browser handles revalidation itself, so it cannot occur. Before 3b a 304 gave a falsy `error`; now fetch would reject. If ever needed: `if (response.status === 304) return response`. No action.

## Checked, closed
### api.ts middleware (shared by all pages)
- openapi-fetch 0.17.0 (`index.mjs:157-177`): `onResponse` results are awaited, an instance of `Response` replaces `response`, falsy keeps it; so the async function and the returned `Response` are allowed. Middleware run in reverse registration order for responses; only one middleware here.
- Order inside `onResponse`: the 401 rule runs first (token and `Authorization` header compared as before), then the ok check, then the envelope check. 401 clears once and calls `unauthorized()` once; the new test asserts `toHaveBeenCalledOnce`, token null, error envelope, status 401. A 401 from core with its body passes through and still ends the session; a 401 to a signed-out request or a replaced token is replaced by the envelope only, session untouched (existing tests still green).
- Body read from `response.clone()`; on pass-through the original is returned unread, so openapi-fetch's `response.text()` works (a core error with `field` is byte-identical: test asserts the exact object). On replacement the new Response is `Response.json`: no `Content-Length`, so openapi-fetch takes the `text()` then `JSON.parse` path and `error` is the envelope; status kept.
- Success: `if (response.ok) return response` before any read; 204 and success-without-body are untouched (test: sign-out 204 gives `error` undefined). `HEAD`: unused by the app, and an ok HEAD is untouched. Not-ok bodies in the edge shapes, run in node with the same expression: `{}`, `[]`, `"x"`, `null`, `{"error":"text"}`, `{"error":{}}`, empty body with a JSON type all give "not core's" and are replaced; `{"error":{"code":"x"}}` passes. A body of `{"error":{"code":"x"}}` with extra fields passes whole.
- Network error: `fetch` rejects before middleware `onResponse`; openapi-fetch rethrows (onError not registered); untouched. Callers that already `.catch` (sign-out, service-areas) are unaffected.
- Image upload (`image.tsx:44-48`) uses the same `api.PUT` with a `bodySerializer` FormData; the middleware touches only the Response, so multipart is unaffected.
- Call sites: 20 `if (error) throw error.error` sites (catalog, stores, stock, product/store forms, image, categories, sign-in, `meQuery`, deletes, PATCH) all now see the envelope on a proxy failure, as the brief wants. None relied on falsy `error` for a not-ok answer: previously `meQuery` on a bodyless 502 resolved `undefined` data (which React Query itself rejects), sign-in on a bodyless 5xx would `throw undefined`/continue with no data; now they throw `{code:'internal',message}`, the existing generic-error paths. `service-areas.tsx` reads `error?.error` and takes `code !== 'conflict'` to the generic text: unchanged behaviour. Guard `_staff.tsx` rethrows non-401 errors to the route error boundary: now with a real object.
- Tests (`api.test.ts`): they import the real `api` and `fakeCore` stubs global `fetch`, so the real openapi-fetch and middleware run. Each would fail on regression: remove the replacement and the 4 failure cases and the 401 case get `""`/`undefined`; replace unconditionally and "core's error unchanged" fails; touch successes and the 204 case fails; the 401 case checks token, call count, envelope, status. Gap, minor: no case for `{"error":"text"}` or `{"error":{}}` (verified by hand above), no test that the success body stays readable (covered by every other page's tests).
