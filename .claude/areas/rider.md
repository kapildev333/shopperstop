## Phase 3 work package (orchestrator, 2026-10-15)
One service and one app, the same shape as core and the two apps. Conventions are CLAUDE.md's: `/api/rider/v1/<plural-kebab-noun>`, one error envelope `{"error": {"code", "message", "field"?}}` with core's codes, lists `{items, page, pageSize, total}`, camelCase JSON with no `null`, `SHOPPERSTOP_RIDER_` env, snake_case tables with `created_at`/`updated_at`, money in cents. Domain words: rider, delivery (one rider carrying one order), store (core's id), order (core's id and number). Never "driver", "trip", "job".

### rider-P3-L1 `rider-service-foundation` (seeds `rider-service`)
- Module `github.com/kapildev333/shopperstop/services/rider`, Go 1.27, `go-chi/chi/v5`, `jackc/pgx/v5`, `golang.org/x/crypto`, sqlc output; `cmd/rider`, `cmd/rider-admin` (`migrate`, `seed-demo --reset`, `create-rider <email> --store <id>`), `migrations/`, `queries/`, `sqlc.yaml`, `internal/`, `openapi.json` (`servers: [{url: "/api/rider/v1"}]`, tag per capability, `securitySchemes.bearer`, `security` on every authenticated operation, an example on every response with content; the contract test from core, adapted).
- Config (fail fast): `SHOPPERSTOP_RIDER_DATABASE_URL`, `SHOPPERSTOP_RIDER_ADDR` (`:8081`), `SHOPPERSTOP_RIDER_SESSION_PEPPER` (32 bytes or more), `SHOPPERSTOP_RIDER_WEB_ORIGINS`, `SHOPPERSTOP_RIDER_CORE_URL` (`http://localhost:8080`), `SHOPPERSTOP_RIDER_CORE_SERVICE_TOKEN`, `SHOPPERSTOP_RIDER_LOG_LEVEL` optional. The Makefile (platform-P3-L1) passes dev and e2e values; `make e2e` uses `shopperstop_rider_e2e`, `:18081`, origins 15173 to 15175.
- `internal/httpx` and `internal/pg` copied from core (D31): error envelope, JSON limits and NUL refusal, request log with route pattern and subject, `X-Request-Id`, CORS from `WEB_ORIGINS`, limiter (10 sign-ins per email and 100 per IP per hour), `Page`, `IsUUID`; wrong method 404 like core. Note the copy's origin commit in `design.md`.
- Migrations: `0001_init.sql` baseline, `0002_riders.sql`: `riders` (`id uuid`, `store_id uuid` not null, `email citext unique`, `name text`, `phone text`, `password_hash text`, `is_active bool`, timestamps), `sessions` (`id`, `rider_id`, `token_hash`, `expires_at`, timestamps; 30-day sliding, peppered, bcrypt cost 12, same shape as core's `internal/auth`). `updated_at` trigger as core.
- `internal/core`: a typed client over `net/http` with the service token (`Stores()`, `Store(id)`, `StoreOrders(id, status)`, `Order(id)`, `ChangeStatus(id, status, actor)`), and token introspection `StaffFromToken(token)` and `CustomerFromToken(token)` (forwarding the bearer to `GET /admin/me` and `GET /me`), cached 30 s per token hash, a core 401 is the caller's 401, any other core failure is 502 `{code: "internal"}` logged with the request id. `internal/coretest`: an `httptest.Server` fake of those routes for the suites (D31); every scenario runs against the real `shopperstop_rider_test` database.
- Routes: `POST /auth/sign-in` `{email, password}` → 200 `{token, rider}` (inactive rider 401, limiter 429 `rate_limited`); `POST /auth/sign-out` 204; `GET /me` → `Rider` (`id`, `storeId`, `email`, `name`, `phone`, `isActive`). Staff routes (core staff token through introspection): `GET /admin/riders?store=&page=` (admin: all stores, `store` filter; store staff: own store only, another store 403), `POST /admin/riders` `{storeId, email, name, phone, password}` 201 (store staff may create only for their store; unknown store 400 `storeId` via core `GET /admin/stores/{id}`... use `Store(id)` through the public `GET /stores/{id}`), `GET|PATCH /admin/riders/{id}` (`name`, `phone`, `isActive`, `password`; deactivating ends the rider's sessions). `GET /healthz`, `GET /readyz` (database ping) in the contract (D16).

Report the ids under `## Requests` to platform for the Postman environment.
- Tests: `go test -race` per package with a fresh schema per package like core; `internal/app` through the real router for riders, staff (admin and store staff via the fake core) and anonymous; the contract test; a seed idempotence test. Gates: `make test-rider` (gofmt, vet, race), `make gen postman` clean, `openspec validate --all --strict`.

### rider-P3-L2 `rider-deliveries` (seeds `deliveries`)
- Migration `0003_deliveries.sql`: `deliveries` (`id`, `order_id uuid unique`, `order_number text`, `store_id`, `rider_id`, `status delivery_status` enum `assigned | delivered`, `customer_name`, `customer_phone`, `address_line1`, `address_line2`, `address_pincode`, `total_cents`, `payment_method`, `item_count`, `assigned_at`, `delivered_at null`, timestamps) and `rider_locations` (`rider_id` primary key, `lat`, `lng`, `recorded_at`). Snapshots copied from core's `Order` at claim so the rider's list works without core.
- `GET /me/ready-orders` → core `StoreOrders(rider.storeId, "ready")` minus orders already claimed, as `{items: [{orderId, number, placedAt, itemCount, totalCents, pincode, customerName}]}`.
- `POST /me/deliveries` `{orderId}`: in one transaction insert the delivery (duplicate `order_id` → 409 `conflict` "already claimed"), then core `ChangeStatus(orderId, "out_for_delivery", {type: "rider", id, name})`; a core 409 (not `ready` any more) or 404 rolls back and answers 409 `conflict` / 404 `not_found`; an order at another store is 404. 201 `Delivery`.
- `GET /me/deliveries?status=assigned|delivered&page=` (default `assigned`), `GET /me/deliveries/{id}` (another rider's is 404), `POST /me/deliveries/{id}/delivered` (only while `assigned`, else 409; core `delivered` with the rider actor in the same request; a core failure leaves the delivery `assigned`), `PUT /me/location` `{lat, lng}` (upsert, 204; `lat` in [-90, 90], `lng` in [-180, 180], else 400 naming the field).
- `GET /orders/{orderId}/delivery` with a customer token: ownership through core `GET /orders/{id}` with that token (404 when not theirs); 404 when no delivery; answers `{riderName, status, location?: {lat, lng, recordedAt}}` where `location` is omitted until the rider posted one. No phone, no email of the rider.
- Seed: a `delivered` delivery by rider `...0801` for core's delivered demo order (`...0701`, `SS-DEMOAAAB`, D20; `...0703` is the placed demo order) with fixed id `...0901`. Log every claim and delivered as core logs transitions.
- Tests include: concurrent claims of one order (exactly one 201); claim rolled back when the fake core answers 409; delivered after core fails stays `assigned`; store isolation; the customer read with another customer's token.

### rider-P3-L3 `rider-app` (seeds `rider-app`)
- `apps/rider/`: React 19, Vite 8, TanStack Router (file-based) and Query, Tailwind 4 with `@shopperstop/ui/tokens.css`, `openapi-fetch` 0.17.0 against `/api/rider/v1` with `paths` from `@shopperstop/ui/api/rider` (ui-P3-L2), Vitest and Testing Library, Playwright with axe. Served under `/rider/` (Vite `base`, router `basepath`), dev 5175 proxying `/api` to core 8080 and rider 8081, preview 15175. `no-literal-colors.test.ts` like the other apps. Token in `localStorage` `shopperstop:rider-token`, cleared on a 401 that answers a request carrying it (admin's rule).
- Pages, phone-first at 390 px (Figma `Rider web` section on the `Admin web` page, drawn by the orchestrator): `/sign-in`; `/` "Ready to pick up": cards (number, time since placed, item count, total, pincode) polling every 10 s, one "Pick up" button each with a confirm `Dialog`, a claimed-by-someone-else 409 shown as a `StatusMessage` and the list refetched; `/deliveries/{id}`: customer name, address, a `tel:` link on the phone (`ButtonLink`), items table (`stack`), total with "Collect ₹X cash" for COD, "Mark delivered" with a confirm `Dialog`; while the delivery is `assigned` the page posts the Geolocation API position every 15 s (`navigator.geolocation.watchPosition`, errors shown once as a `StatusMessage`, never blocking); `/history`: delivered deliveries table. Header: store name (core public `GET /stores/{id}`), rider name, Sign out. Every page composes `@shopperstop/ui` only; large tap targets; the list region uses `aria-live="polite"` for new ready orders.
- e2e (`apps/rider/e2e`, Chromium, `geolocation` permission and a fixed position in the context): sign-in, ready list, pick up, delivery page, location posted (assert through the customer read), delivered, history, axe on every page. The Phase 3 cross-app flow lives here and drives the web (15173), admin (15174) and rider (15175) previews: the customer places an order, store staff move it to `ready` on the board, the rider picks it up and marks it delivered, the customer's tracking shows the rider's name and then delivered. The Playwright config starts core (18080) and rider (18081) from `make e2e`'s env and builds the three previews.
