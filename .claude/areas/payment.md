## Requests
- from core (core-P5-L1 review, relayed by the orchestrator 2026-10-16, for payment-P5-L2): `POST /admin/orders/{id}/payment` does not check the order status, so a `paid` arriving after the timeout sweep cancelled the order still lands (`pending` to `paid` on a cancelled order) and core refunds nothing by itself. The payment service handles the race: on a gateway `paid` for an order it reads as `cancelled`, mark the payment paid, then refund at the gateway and mark core `refunded` (one scenario and test). Core's guard: the service's system cancel is accepted only while `paymentStatus` is `pending` (409 `conflict` otherwise), so the timeout can never cancel a paid order.
- from core (core-P5-L1 proposal b969350, relayed by the orchestrator 2026-10-16): the payment service token reaches only `GET /admin/orders/{id}`, `POST /admin/orders/{id}/status` (cancel only, `actor {type: system, name}`), `POST /admin/orders/{id}/payment` and `GET /admin/order-events`; a repeated `paid` is 409 (read the order after a 409); payment events in the feed keep `fromStatus == toStatus` with `actorType system`, `actorName payment` (skip them in the refund worker); the demo paid order is SS-DEMOAAAE (...0704) with reference `fake_demo_0a01`, so the demo payment ...0a01 carries gateway ref `fake_demo_0a01`. ## Phase 5 work package (orchestrator, 2026-10-16)
One service, the same shape as rider. Conventions are CLAUDE.md's: `/api/payment/v1/<plural-kebab-noun>` (`/me/payments`, `/orders/{orderId}/payment`, `/webhooks/razorpay`, `/fake/{id}`), one error envelope with core's codes, lists `{items, page, pageSize, total}`, camelCase JSON with no `null`, `SHOPPERSTOP_PAYMENT_` env, snake_case tables with `created_at`/`updated_at`, money in cents. Domain words: payment (one attempt to pay one order), gateway (the outside party), order (core's id and number), customer (core's id). Never "transaction", "txn", "checkout" for a payment, "user".

- Layout (Spec 2 §9, as rider): `cmd/payment`, `cmd/payment-admin` (`migrate`, `seed-demo [--reset] [--force]` with core's local-database guard), `internal/config`, `internal/httpx` and `internal/pg` (copies, D52), `internal/core` (client with the service token, the two forwarded customer reads, token introspection as rider's), `internal/gateway` (`Gateway` interface: `CreateLink(ctx, payment) (ref, payUrl, error)`, `Refund(ctx, payment) (ref, error)`, `ParseWebhook(r) (event, error)`; `fake` and `razorpay` packages beneath it), `internal/payment` (rows, handlers, the outcome function shared by the fake result, the webhook and the sweep), `internal/tail` (the cursor loop over core's events feed), `internal/app`, `internal/seed`, `internal/testdb`, `openapi.json`.
- Tables: `payments` (`order_id uuid unique`, `customer_id`, `amount_cents bigint`, `status payment_status` `created|paid|failed|refunded`, `gateway text`, `gateway_ref text`, `pay_url text`, `return_url text`, `expires_at timestamptz`, `paid_at`, `refunded_at`, `failure_reason text`), `cursors` (`name text primary key`, `seq bigint`). One open (`created`) payment per order at a time: a second `POST /me/payments` for the same order answers the open one (200); a `failed` payment lets a new one be created (the unique index is partial on `status = 'created'`).
- Flow (D50): create reads the order through core with the customer's token (must be `online`, `paymentStatus` `pending`, the customer's own; `amountCents` is the order's `totalCents`, frozen), asks the gateway for a link, stores the row, answers 201. Success (fake result, or webhook `payment_link.paid`) marks `paid` and then calls core `paid` with the gateway reference; a core failure is logged and retried by the sweep (the row carries `core_synced bool`). Failure marks `failed`. The sweep every 30 s: payments `created` past `expiresAt` (15 minutes after the order's `placedAt`, read once at create) are marked `failed` and the order cancelled through core with the system actor (idempotent: a 409 from core because the order moved on is logged, not retried). The refund worker tails the feed from the `refunds` cursor: a `cancelled` event for an order whose payment is `paid` asks the gateway for a refund, marks `refunded` and calls core `refunded`.
- The fake gateway (D49): `CreateLink` returns `<PUBLIC_URL>/api/payment/v1/fake/{id}`; `GET` serves a plain HTML page (no script, no design system: a form with "Pay ₹<amount>" and "Fail payment"); `POST /fake/{id}/result` applies the outcome and 303-redirects to `returnUrl`; `Refund` succeeds at once. Only when `SHOPPERSTOP_PAYMENT_GATEWAY=fake`; the routes answer 404 under `razorpay`.
- Razorpay (D49, L3): payment links (`POST https://api.razorpay.com/v1/payment_links` with `amount`, `currency: INR`, `reference_id` = payment id, `callback_url` = `returnUrl`, `callback_method: get`), refunds (`POST /v1/payments/{paymentId}/refund`), webhook signature `X-Razorpay-Signature` = hex HMAC-SHA256(body, webhook secret), events `payment_link.paid` and `refund.processed`; the base URL is configurable so tests point at `httptest`. Recorded shapes live in `internal/gateway/razorpay/testdata/`.
- Auth: customer routes verify the bearer through core's `GET /me` as rider does (no customer table here); the webhook route has no bearer (signature only); the fake routes are public (local only). Rate limit: core's limiter copy on `POST /me/payments` (10 per customer per hour).
- Tests (Spec 2 §13): the real `shopperstop_payment_test` database, a fake core at the process boundary (`internal/coretest` as rider's: the order read, the payment route, the status route, the events feed), the fake gateway in-process, `httptest` Razorpay for L3; `make e2e` exercises the real core through the web, mobile and admin suites (their flows drive the fake page). Contract test, Postman collection, examples on every route.
- Logging (Spec 2 §12): one line per request, one per payment transition with the order number, one per sweep or tail batch that did work, errors with the request id.
