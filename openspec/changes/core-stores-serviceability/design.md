# Design

## Context
Builds on `core-accounts-auth` (core-P2-L1), which merges before any worker of this change starts; this branch is rebased onto it. From L1 this change uses, without redefining: migration `0002_accounts.sql` (`staff_users`, `set_updated_at()`), `sqlc.yaml` (v1.31.1, uuid as `string`), `pg.Map` / `pg.IsUnique`, `testdb.Migrated`, `httpx.ReadJSON` / `ReadPatch` / `Page` / `NewList` / `PathID` / `WriteJSON` / `WriteError`, `auth.RequireAdmin`, `app.New(pool, origins, a)`, the `app` test fixtures (shared `srv`, `testPool`, `call`, a customer, an admin and a store-staff token, `TestAuthGates`), the contract test with its security check (L1 Decision 24), and `seed.Reset` / `Load` (L1 Decision 21). Behaviour comes from this change's deltas (`serviceability`, `admin-stores`, `admin-staff`). PLAN.md D3, D19, D20, D22 apply.

A spike on 2026-10-12 (scratch copy of L1's branch at b68fb55, sqlc v1.31.1, `shopperstop_core_test`) confirmed the migration, the `sqlc.yaml` block and `queries/store.sql` below verbatim: they generate and compile; every store query returns the model `db.Store`; a second store taking a served pincode fails with `23505 store_service_areas_pincode_key`; `PincodeHolder` returns the lowest held pincode and `pgx.ErrNoRows` for none or an empty array; `AddServiceAreas` with an empty array inserts nothing; deleting a store cascades to its service areas; a store-staff insert with an unknown store and a delete of a store with staff both fail with `23503 staff_users_store_id_fkey`; `0003` applies over a pre-existing orphan `store_staff` row (`not valid`) and later updates of that row that do not touch `store_id` still succeed; `truncate sessions, addresses, customers, staff_users, store_service_areas, stores` succeeds. Workers copy these; they do not redesign them.

### Assumptions about core-P2-L1 (check after the rebase)
Names are L1's design.md as of 5f695b7. If a name differs on main, the worker uses main's name and notes it in the lane log; if a behaviour differs, the worker stops and reports.
- `httpx.PathID(r, "id") (string, error)`: canonical uuid or a 404 `not_found` `*httpx.Error`.
- `httpx.Page(r) (page, pageSize int, err error)`; `httpx.NewList(items, page, pageSize, total)`.
- `httpx.ReadPatch(w, r, &dst)`: object only, explicit `null` refused naming the member.
- `a.RequireAdmin`: 401 without a staff session, 403 `forbidden` "admins only" for store staff.
- `internal/app` tests: `testPool`, `srv`, `call(t, method, path, token, body) (int, []byte)`, `sync.Once` fixtures with a customer token, an admin token and a store-staff token, and the `TestAuthGates` table.
- `seed.Reset` truncates a table list then calls `Load`, which inserts fixed rows with `tx.Exec` and hashes with `auth.HashPassword`.
- `auth.CreateStaff` inserts with `CreateStaff` and maps errors with `pg.IsUnique` / `pg.Map`.

## Goals / Non-Goals
**Goals:** every scenario in the three deltas has a Go test through the real database (and the real router for HTTP scenarios); later core lanes get `store.Get` and `store.ForPincode`; the seed has the two stores and their staff with fixed ids.

**Non-Goals:** store `slug`, `lat`, `lng`; opening hours; any order logic (the orders half of "delete only with no orders" is core-P2-L5's, see Decision 5); Postman environment values (platform).

## Schema: `migrations/0003_stores.sql` (verbatim)
```sql
-- Stores and the pincodes each one delivers to; staff users now reference their store.
create table stores (
    id                        uuid primary key default gen_random_uuid(),
    name                      text not null,
    address_line              text not null,
    pincode                   text not null,
    is_open                   boolean not null default false,
    delivery_fee_cents        bigint not null default 0 check (delivery_fee_cents >= 0),
    free_delivery_above_cents bigint not null default 0 check (free_delivery_above_cents >= 0),
    min_order_cents           bigint not null default 0 check (min_order_cents >= 0),
    promised_minutes          integer not null check (promised_minutes > 0),
    created_at                timestamptz not null default now(),
    updated_at                timestamptz not null default now()
);
create trigger stores_updated_at before update on stores for each row execute function set_updated_at();

create table store_service_areas (
    id         uuid primary key default gen_random_uuid(),
    store_id   uuid not null references stores (id) on delete cascade,
    pincode    text not null unique,
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now()
);
create index store_service_areas_store_id on store_service_areas (store_id);
create trigger store_service_areas_updated_at before update on store_service_areas for each row execute function set_updated_at();

-- not valid: rows written before this migration are not checked (a fresh database has none);
-- every insert and update from now on is, and a referenced store cannot be deleted.
alter table staff_users add constraint staff_users_store_id_fkey
    foreign key (store_id) references stores (id) not valid;
```

### `queries/store.sql` (verbatim)
```sql
-- name: GetStore :one
select * from stores where id = $1;

-- name: StoreForPincode :one
select s.*
from store_service_areas a join stores s on s.id = a.store_id
where a.pincode = $1;

-- name: ListStores :many
select * from stores order by name, id limit $1 offset $2;

-- name: CountStores :one
select count(*) from stores;

-- name: CreateStore :one
insert into stores (name, address_line, pincode, is_open, delivery_fee_cents, free_delivery_above_cents, min_order_cents, promised_minutes)
values ($1, $2, $3, $4, $5, $6, $7, $8)
returning *;

-- name: UpdateStore :one
update stores
set name = coalesce(sqlc.narg(name), name),
    address_line = coalesce(sqlc.narg(address_line), address_line),
    pincode = coalesce(sqlc.narg(pincode), pincode),
    is_open = coalesce(sqlc.narg(is_open), is_open),
    delivery_fee_cents = coalesce(sqlc.narg(delivery_fee_cents), delivery_fee_cents),
    free_delivery_above_cents = coalesce(sqlc.narg(free_delivery_above_cents), free_delivery_above_cents),
    min_order_cents = coalesce(sqlc.narg(min_order_cents), min_order_cents),
    promised_minutes = coalesce(sqlc.narg(promised_minutes), promised_minutes)
where id = @id
returning *;

-- name: DeleteStore :execrows
delete from stores where id = $1;

-- name: LockStore :one
select id from stores where id = $1 for update;

-- name: ListServiceAreas :many
select pincode from store_service_areas where store_id = $1 order by pincode;

-- name: PincodeHolder :one
select pincode, store_id from store_service_areas
where pincode = any(@pincodes::text[]) and store_id <> @store_id
order by pincode limit 1;

-- name: DeleteServiceAreas :exec
delete from store_service_areas where store_id = $1;

-- name: AddServiceAreas :exec
insert into store_service_areas (store_id, pincode)
select @store_id::uuid, unnest(@pincodes::text[]);
```
sqlc expands `select *` and `returning *` into the column list at generation time, so every store query returns `db.Store` (`ID string`, `Name`, `AddressLine`, `Pincode string`, `IsOpen bool`, `DeliveryFeeCents`, `FreeDeliveryAboveCents`, `MinOrderCents int64`, `PromisedMinutes int32`, `CreatedAt`, `UpdatedAt pgtype.Timestamptz`). `UpdateStoreParams` has pointer fields plus `ID`. `ListServiceAreas` returns `[]string` (nil when empty).

## Interfaces
```go
// internal/store
type Store struct { // public view: GET /stores/{id}, serviceability, and later cart and orders
    ID                     string `json:"id"`
    Name                   string `json:"name"`
    IsOpen                 bool   `json:"isOpen"`
    DeliveryFeeCents       int64  `json:"deliveryFeeCents"`
    FreeDeliveryAboveCents int64  `json:"freeDeliveryAboveCents"`
    MinOrderCents          int64  `json:"minOrderCents"`
    PromisedMinutes        int32  `json:"promisedMinutes"`
}
type AdminStore struct { // admin view: Store plus the store's own address
    Store
    AddressLine string `json:"addressLine"`
    Pincode     string `json:"pincode"`
}

// For other packages (cart in L4, order placement in L5). q is a pool or a pgx.Tx.
func Get(ctx context.Context, q db.DBTX, id string) (Store, error)             // no rows -> 404 not_found (pg.Map)
func ForPincode(ctx context.Context, q db.DBTX, pincode string) (Store, error) // no rows -> 404 not_serviceable

// Handlers, each func(pool *pgxpool.Pool) http.HandlerFunc:
// Serviceability, PublicGet, List, Create, AdminGet, Update, Delete, ServiceAreas, ReplaceServiceAreas
```
`db` is `internal/store/db`; `db.DBTX` is sqlc's interface that both `*pgxpool.Pool` and `pgx.Tx` satisfy.

## Handler behaviour
- **Serviceability**: `p := r.URL.Query().Get("pincode")`; not matching `^[1-9][0-9]{5}$` → 400 `validation` "pincode must be 6 digits" field `pincode`; `ForPincode` → 200 `{"store": Store}`; its 404 is `{"code":"not_serviceable","message":"we do not deliver to this pincode yet"}`.
- **PublicGet**: `PathID` → `Get` → 200 `Store`.
- **List**: `Page` → `ListStores(limit=pageSize, offset=(page-1)*pageSize)` and `CountStores` → 200 `NewList([]AdminStore, page, pageSize, total)`.
- **Create**: `ReadJSON` into `fields` (below); nil `name`, `addressLine`, `pincode` become `""`, nil `promisedMinutes` becomes 0, nil `isOpen` false, nil money 0; `check` → `CreateStore` → 201 `AdminStore`.
- **AdminGet**: `PathID` → `GetStore` (`pg.Map`) → 200 `AdminStore`.
- **Update**: `PathID` → `ReadPatch` into `fields` → `check` (present fields only) → `UpdateStore` (no rows → `pg.Map` 404) → 200 `AdminStore`. `{}` answers the store unchanged.
- **Delete**: `PathID` → `DeleteStore`; error → `pg.Map` (23503 → 409 `conflict` "still in use"); 0 rows → 404; else 204 no body.
- **ServiceAreas**: `PathID` → `GetStore` (404) → `ListServiceAreas` → 200 `{"pincodes": [...]}`, a nil slice written as `[]`.
- **ReplaceServiceAreas**: `PathID` → `ReadJSON` into `struct{ Pincodes []string \`json:"pincodes"\` }`; nil (absent or `null`) → 400 "pincodes is required"; more than 100 entries → 400 "at most 100 pincodes"; any entry not matching the pincode pattern → 400 "every pincode must be 6 digits"; all with field `pincodes`. Then `slices.Sort` + `slices.Compact`. In `pgx.BeginFunc(ctx, pool, ...)` with `q := db.New(tx)`: `LockStore` (no rows → 404), `PincodeHolder` (a row → return `&pincodeConflict{Pincode, StoreID}`; `pgx.ErrNoRows` → go on), `DeleteServiceAreas`, `AddServiceAreas`. Commit → 200 `{"pincodes": <sorted, deduplicated list>}`. On `*pincodeConflict` the handler writes 409 `{"error":{"code":"conflict","message":"pincode <p> is served by another store","field":"pincodes","pincode":"<p>","storeId":"<id>"}}` with `httpx.WriteJSON`; any other error goes through `pg.Map` and `httpx.WriteError`.

`fields` is one struct for create and patch:
```go
type fields struct {
    Name                   *string `json:"name"`
    AddressLine            *string `json:"addressLine"`
    Pincode                *string `json:"pincode"`
    IsOpen                 *bool   `json:"isOpen"`
    DeliveryFeeCents       *int64  `json:"deliveryFeeCents"`
    FreeDeliveryAboveCents *int64  `json:"freeDeliveryAboveCents"`
    MinOrderCents          *int64  `json:"minOrderCents"`
    PromisedMinutes        *int32  `json:"promisedMinutes"`
}
```
`check(f *fields) error` trims `Name` and `AddressLine` in place and checks the present fields in this order, first failure wins, each 400 `validation` with the JSON name in `field`: `name` 1 to 100 runes ("name must be 1 to 100 characters"), `addressLine` 1 to 200 runes, `pincode` pattern ("pincode must be 6 digits"), `deliveryFeeCents`, `freeDeliveryAboveCents`, `minOrderCents` each 0 to 10 000 000 ("must be 0 to 10000000"), `promisedMinutes` 1 to 240. A JSON number that does not fit the Go type (a fraction, a string) is `ReadJSON`'s 400 "invalid JSON" without a field.

`auth.CreateStaff` (L1's function): before its existing `pg.Map`, a `*pgconn.PgError` with code `23503` returns `&httpx.Error{Status: 400, Code: "validation", Message: "no such store", Field: "storeId"}`.

## Decisions
1. **Ownership.** `internal/store` owns `stores` and `store_service_areas`; other packages read stores through `store.Get` and `store.ForPincode`, never their own SQL. `internal/seed` writes them as the demo loader (as in L1 Decision 1). Ceiling: none.
2. **No `slug`, `lat` or `lng` on stores.** Spec 2 §3 lists them, but no route, page or query uses them: web resolves a pincode to a store id, admin addresses stores by id, serviceability is by pincode, not radius (Spec 2 §2). Same call as L1 made for address `lat`/`lng`. Ceiling: add `slug` when a URL names a store, `lat`/`lng` with radius serviceability (Spec 2 §14 trigger: a city with more than three stores). Owner may override.
3. **Two views, one row.** `Store` is the public view (what checkout shows: fees, threshold, minimum, promised minutes, open); `AdminStore` embeds it and adds the store's own address (`addressLine`, `pincode`). Timestamps are not exposed. Ceiling: an internal-only field later goes on `AdminStore` only.
4. **Store staff get 403 on every `/admin/stores` route.** Spec 2 §6 makes these routes admin-only, and `RequireAdmin` answers 403 before the id is read, identically for the staff member's own store, another store or none, so existence does not leak (Spec 2 §5's intent). The 404 isolation rule of Spec 2 §5 applies to routes store staff can reach (stock in L4, orders in L5). Ceiling: none.
5. **"Delete only with no orders" is the database's job.** The delete is a plain `delete`; foreign keys without `on delete` (no action) refuse it with `23503`, which `pg.Map` turns into 409 `conflict` "still in use". Today the referencing rows are staff users (`staff_users_store_id_fkey`); core-P2-L5 adds `orders.store_id references stores (id)` (no `on delete`) and the 409 for orders follows with no code change here; L5 adds that scenario to its delta. Service areas cascade. Ceiling: the message does not say which rows hold the store; the admin page says "remove its staff users first; a store with orders cannot be deleted".
6. **The staff foreign key is `not valid`.** Dev and e2e databases migrated under L1 may hold store staff whose `store_id` names no store (L1 accepted any uuid). `not valid` skips checking those rows, so `migrate` cannot fail on them; every later insert, every update of `store_id` and every store delete is checked, and `seed-demo --reset` truncates the old rows anyway. Ceiling: an orphan row survives in a database that is never reset; `alter table staff_users validate constraint staff_users_store_id_fkey` makes it strict once none are left.
7. **Service-area replace: lock, check, delete, insert, one transaction.** `LockStore` (`for update`) serialises two replaces of the same store and gives the 404. `PincodeHolder` finds the lowest requested pincode another store serves, so the 409 can name the store (Spec 2 §6). Ceiling: two admins claiming the same new pincode for two different stores at the same instant: the loser's insert hits the unique index and gets `pg.Map`'s 409 "already exists" without `storeId`; a retry names the store.
8. **The conflict's extra members are written by the handler.** `httpx.Error` stays `{code, message, field}`; this one 409 writes `pincode` and `storeId` beside them and `openapi.json` documents it as its own schema `PincodeConflict`. Ceiling: when core-P2-L5 adds `productIds` to `out_of_stock`, move both into optional `httpx.Error` fields if a third case appears.
9. **Defaults and ranges.** A new store is closed unless `isOpen` is sent (an admin sets pincodes, then opens it); absent money fields are 0 (no fee, threshold 0 means always free, no minimum). Money 0 to 10 000 000 cents (₹1,00,000) and `promisedMinutes` 1 to 240 catch typos; the database checks only non-negative and positive. Ceiling: none.
10. **Service areas are one document of at most 100 pincodes.** Spec 2 §6 replaces the list as a whole, so it is read and written whole, not paged (the platform paging rule is for collections of resources). Bengaluru has about 100 delivery pincodes. Ceiling: raise the cap with the first store that needs more.
11. **No opening hours.** Spec 2 has only `is_open`, a switch an admin flips. Ceiling: an hours table when the owner asks.
12. **Fixed demo rows (D20, D22).** Added to L1's seed in `Load` (stores and service areas before the store staff) and to the `truncate` list (`store_service_areas, stores`). Service-area rows take generated ids (nothing refers to them). One `auth.HashPassword("staff12345")` serves both staff rows.

13. **`openapi.json` shapes.** Tags appended after L1's: `serviceability` ("Which store delivers to a pincode, and its public details"), `admin-stores` ("Admin management of stores and the pincodes they serve"). Schemas: `Store` (7 required members, ids `format: uuid`, money `integer` `format: int64`), `AdminStore` (`allOf` `Store` plus `addressLine`, `pincode`), `StoreCreate` (required `name`, `addressLine`, `pincode`, `promisedMinutes`), `StorePatch` (all optional, `minProperties` not set), `StoreList` (`{items: AdminStore[], page, pageSize, total}`), `Serviceability` (`{store: Store}`), `ServiceAreas` (`{pincodes: string[]}`, also the PUT body), `PincodeConflict` (`{error: {code, message, field, pincode, storeId}}`). Path parameter `id` example `00000000-0000-4000-8000-000000000401` on every store route; query `pincode` example `560034`; `page`/`pageSize` on the list. Examples: Koramangala as every store example; request bodies POST `{"name":"HSR Layout","addressLine":"27th Main, HSR Layout","pincode":"560102","promisedMinutes":12,"deliveryFeeCents":2500,"freeDeliveryAboveCents":19900,"minOrderCents":9900}`, PATCH `{"promisedMinutes":10}`, PUT `{"pincodes":["560034","560095"]}` (the seed's own values, so a top-to-bottom Postman run against `make dev` changes nothing; its DELETE answers 409 because the demo store has staff). Every error response with the `Error` schema and the code and message the handler writes; 401 and 403 examples as L1's ("sign in required", "admins only"); `security: [{"bearer": []}]` on the seven admin operations only.
14. **L1 test fixtures.** After `0003`, inserting a store-staff user with an invented `store_id` fails. Every L1 test or fixture that does so inserts a store first with `insert into stores (name, address_line, pincode, promised_minutes) values ('Test store', '1 Test Rd', '560001', 10) returning id` (or, through the API, creates one with `POST /admin/stores`). Assertions do not change. These edits ride in task 1's `feat:` commit because the `stores` table they need arrives there.

## Test strategy
`make test-core` on `shopperstop_core_test`. `internal/store` tests use `testdb.Migrated("store")` and the Go API with real SQL. `internal/app` tests share one schema (`Migrated("app")`), so every test creates its own stores with `testPool` or the API and uses pincodes no other test uses (stores tests `5611xx`, admin store tests `5612xx`, service-area tests `5613xx`, staff test none); counts are compared with `select count(*)` rather than fixed numbers. Route tests go through `srv` and check status, envelope `code`, `field`, and body shape (exact key sets for `Store`). The auth matrix extends L1's `TestAuthGates` with the seven admin store routes: anonymous 401, customer 401, store staff 403, admin allowed (2xx or a validation/404 answer for the zero id). The contract tests (`TestContract`, `TestContractSecurity`) must stay green: every route documented, `security` exactly on the admin ones. `internal/seed` tests reset twice and read rows and HTTP answers through `app.New` on an `httptest` server, like L1's.

## Risks / Trade-offs
- [L1's names or fixtures differ on main from its design] → assumptions listed above; the worker adapts names and reports, stops on behaviour.
- [Fixture edits in L1's test files are outside this lane's own packages] → unavoidable consequence of the foreign key L1 requested; limited to inserting a store before a store-staff row (Decision 14). Manager's scope call.
- [`internal/auth/staff.go` is L1's file] → one error branch, requested by L1 in its lane log; nothing else in `auth` changes.
- [`make postman` and `scripts/postman.test.mjs`] → same dependency as L1's escalation (the test's folder-count assertion; committing the regenerated collection from a core PR). This change follows whatever the manager decided for L1.
- [Postman's POST example creates an "HSR Layout" store on every collection run] → harmless; `seed-demo --reset` removes it.
- [`store_stock`, `carts` and `orders` reference stores in later lanes] → their `on delete` choice decides whether a store with stock or carts can be deleted; recommended in the lane log: stock and carts cascade, orders no action (Decision 5).

## Migration Plan
`core-admin migrate` applies `0003` after `0002`. Rollback is not automated (no down migrations, Phase 1 rule): drop `staff_users_store_id_fkey`, `store_service_areas`, `stores`, and delete the `0003` row from the migrations table.
