# Design

## Context
`openspec/specs/` is empty and this OpenSpec version (1.14.1) has no CLI sync command: `/opsx:sync` (`.claude/commands/opsx/sync.md`) is agent-driven, the agent reads the deltas and edits the main specs. `openspec archive` also applies deltas, but project rules archive only after the feature PR merges, and the living specs must exist on the feature branch itself. The requirement text is fixed by plan Task 3 steps 2 and 3; see proposal.md for why.

## Goals / Non-Goals
**Goals:** both living specs on the branch, byte-identical to the plan's text; `openspec validate --all --strict` green with the change still active.

**Non-Goals:** rewording, adding or reordering requirements; seeding other capabilities (D4); archiving (the area manager archives by PR after merge).

## Decisions
- **Deltas are the plan's requirement blocks verbatim under `## ADDED Requirements`.** Generated by cutting the plan's fenced spec text from the first `### Requirement:` to the end, so a diff proves fidelity. Alternative, paraphrasing to fit OpenSpec style: rejected, the plan's text already meets the strict validator.
- **Apply with `/opsx:sync`, agent-driven.** Sync of an ADDED-only delta into a missing main spec means writing the file as header + requirements. The header (`# <capability>`, `## Purpose` paragraph, `## Requirements`) comes from the plan, because deltas carry no Purpose and the archive fallback would write a placeholder Purpose. The result is therefore exactly the plan's fenced text, and the worker checks it with `diff`. Alternative, `openspec archive` on the branch: rejected, it moves the change into `archive/` before review and breaks the archive-after-merge rule.
- **Checked end state:** in a scratch copy, the change plus synced specs validated `3 passed, 0 failed` with `--all --strict`, and a subsequent `openspec archive` reported "Specs already in sync; no files changed". So archiving after merge is a no-op on the specs.

Simplification: a straight copy instead of a merge. Ceiling: valid only because the main specs do not exist yet; every later change must do a real delta merge.

## Risks / Trade-offs
- [Requirements with scenarios that cannot be tested yet (no code exists)] → each scenario is verified by the lane that builds it (core, ui, web, admin); `/opsx:verify` for this change checks only that the specs exist, match the plan and validate.
- [`openspec/config.yaml` `rules.tasks` items contain an unquoted `: `, so the CLI warns on every call and ignores the tasks rules] → out of scope here; raised to the area manager as a one-line follow-up.
