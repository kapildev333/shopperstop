## Context

`apps/admin` is the model: same stack, same session rule, same test fakes, same Playwright shape. The rider app differs in three ways: it talks to two services (rider for everything, core only for the store name), it is phone-first, and its e2e suite owns the Phase 3 cross-app flow. The API it consumes is `services/rider/openapi.json` on main (rider-service-foundation, rider-deliveries), typed by `packages/ui/src/api/rider.d.ts`.

Figma: the team lead could not open the Figma file in this session (no Figma tool loaded), so the pages are designed from Spec 1 §8 and §10 and the admin app's patterns. The manager's phone-width walk compares against the `Rider web` section on the `Admin web` page; a difference is a fix task, not a design change.

## Goals / Non-Goals

Goals: a rider can sign in on a phone, see what is ready, pick an order up, see where to take it and what to collect, report position while on the way, mark it delivered, and see past deliveries. One e2e suite proves the rider flow and the customer to staff to rider flow.

Non-goals: maps, push, offline, delivery proof, cash reconciliation, batches, handing back (D32 ceilings); any file outside `apps/rider/` and this change, except the root `package-lock.json` entries npm writes for the workspace.

## Decisions

1. **Copy admin's skeleton, from `a665845`.** `session.ts`, the `api.ts` middleware (bearer, 401 rule, envelope for answers without one), `router.ts`, `render-app.tsx`, `main.tsx`, `test-setup.ts`, `route-error.tsx`, `not-found.tsx`, `eslint.config.js`, `tsconfig.json`, `index.html`, `index.css`, `no-literal-colors.test.ts` and `package.json` (same pinned versions, name `@shopperstop/rider`) are copied from `apps/admin` at `a665845` and renamed. Router `basepath: '/rider'` (none when a test passes a memory history), Vite `base: '/rider/'`. QueryClient `retry: false`, no `throwOnError` (the rider service has no 403 a page must turn into not found). Ceiling: three apps now carry the same session and client code; a fourth app is the trigger for a shared module in `packages/ui`.
2. **Two clients, the token on one.** `rider` = `createClient<paths>` from `@shopperstop/ui/api/rider`, base `${location.origin}/api/rider/v1`, with the bearer and the 401 rule. `core` = `createClient<paths>` from `@shopperstop/ui/api`, base `${location.origin}/api/core/v1`, envelope middleware only, never a token: the store read is public and a rider token means nothing to core. Both pass `fetch: (r) => globalThis.fetch(r)` (tests stub it).
3. **Dev and preview proxies per service.** `server.proxy = { '/api/core': 'http://localhost:8080', '/api/rider': 'http://localhost:8081' }`, `preview.proxy` the same with 18080 and 18081; `server.port` 5175 and `preview.port` 15175, both `strictPort`.
4. **Every route file lands with task 1.** `__root.tsx`, `sign-in.tsx`, `_rider.tsx` (guard), `_rider/index.tsx`, `_rider/history.tsx`, `_rider/deliveries/$deliveryId.tsx` exist from task 1, the three pages rendering only their `PageHeader` (and the delivery page its `GET` and not found). So `routeTree.gen.ts` and the typed nav links are final after task 1, and tasks 3, 4 and 5 each edit only their own route file and modules, in parallel, without a merge on generated code.
5. **Guard and banner.** `_rider.tsx` `beforeLoad`: no token, redirect to `/sign-in?redirect=<location.href>` with no request; else `context.rider = await queryClient.ensureQueryData(meQuery)`; on a failure with the token gone (401), the same redirect; any other failure goes to `RouteError` ("Could not reach the server." + "Try again"). The root layout reads `rider` from the `/_rider` match like admin reads `staff`, and runs `useQuery(storeQuery(rider.storeId))` for the banner; the store name is rendered only when that query has data, so a pending or failed read hides it and blocks nothing.
6. **Query keys.** `['rider','me']` (`staleTime: Infinity`), `['core','store',id]` (`staleTime: Infinity`), `['rider','ready']` (`refetchInterval: 10_000`), `['rider','deliveries','assigned']`, `['rider','deliveries','delivered']`, `['rider','delivery',id]`. A claim success sets `['rider','delivery',d.id]` to the answer and invalidates `ready` and `assigned`; a delivered success sets the delivery and invalidates `assigned` and `delivered`. Sign-out and the lost-session handler `queryClient.clear()`. TanStack Query keeps `data` when a refetch fails, which gives "later read fails keeps the cards" for free; the page shows the error state only when `data` is absent.
7. **Ready list is a live list.** `<ul aria-label="Ready orders" aria-live="polite">`: new cards are additions, so screen readers announce a new ready order and are silent on removals. No extra `VisuallyHidden` count line (it would repeat the card). Each card is a `Card` with the number (`tabular-nums`, `text-h3`), `useSince(placedAt)` ("12 min ago"), the item count ("1 item" / "3 items"), `Price`, the pincode, and a full-width `Button size="lg"` "Pick up" with `aria-label="Pick up <number>"` (the visible text is part of the name, WCAG label in name).
8. **"Your deliveries" on `/` (beyond the package).** After a pick up the rider lands on the delivery page, but once they leave it (History, a reload of `/`) nothing led back. One `GET /me/deliveries?status=assigned` above the ready list, a `section` with heading `h2` "Your deliveries" and one `Card`-wrapped `Link` per delivery ("<number> <customer name>", `buttonClass({ variant: 'secondary', size: 'lg' })`), rendered only when `items` is non-empty. Ceiling: the first page only (the service's default page size); a rider holds one or two deliveries at a time.
9. **Claim and its refusals.** One `Dialog` per page state (`picking: ReadyOrder | undefined`), `DialogFooter` with Cancel first and `Button loading={claim.isPending}` "Pick up". `useMutation` → `rider.POST('/me/deliveries', { body: { orderId } })`; 201 navigates to `/deliveries/$deliveryId`. On an `ApiError` with code `conflict` or `not_found`: close, set the page's status message "<number> was taken by another rider or is no longer ready." (`StatusMessage tone="warning"`, above the list, until the next pick up) and `invalidateQueries(['rider','ready'])`. Anything else: `ErrorBanner` "Could not pick up the order. Try again." inside the dialog, no retry button (the "Pick up" button is the retry).
10. **Rider's name on the customer's tracking page: through the API for now.** web-P3-L1 (the rider card on web's tracking page) is not on main. The cross-app flow asserts the rider's name with the customer's core token on `GET /api/core/v1/orders/{id}` (`riderName`, the field web-P3-L1 renders) and on the rider service's `GET /api/rider/v1/orders/{orderId}/delivery`; the tracking page itself is asserted with the texts web already shows ("Your order is out for delivery.", "Your order was delivered."). When web-P3-L1 is on main, the rider area adds one `expect` on the page for the rider card (backlog line in the area plan, no spec change: the requirement already says "names the rider").
11. **Delivery page.** `useQuery(deliveryQuery(id))`; an `ApiError` `not_found` renders `NotFound` (the route's `errorComponent` would also catch it, but the query uses `throwOnError: false`, so the page checks `error.code`). Layout top to bottom, one column: `PageHeader title="Order <number>"` with a `Badge` (`accent` "On the way" / `success` "Delivered"); for `assigned` + `cod` a `StatusMessage` "Collect ₹339 cash" (`formatInr` from `@shopperstop/ui/format`); a `Card` "Customer" with the name, `line1`, `line2` when present, the pincode, and `ButtonLink size="lg" href="tel:<phone>"` "Call <name>" (lucide `Phone` 16 px, `aria-hidden`); `Table stack caption="Items"` with columns Product, Unit, Quantity; the total as `Price`; for `assigned` a full-width `Button size="lg"` "Mark delivered". Delivered: `useMutation` → `rider.POST('/me/deliveries/{id}/delivered')`; 200 sets the cache (Decision 6) and the status message `tone="success"` "<number> delivered."; 409 closes and invalidates the delivery; anything else `ErrorBanner` "Could not mark the order delivered. Try again." in the dialog.
12. **Location reporter, one hook.** `src/location.ts` exports `useLocationReport(active: boolean): string | undefined` (the message to show, or nothing). While `active`: if `navigator.geolocation` is missing, return the message; else `watchPosition(onFix, onError, { enableHighAccuracy: true, maximumAge: 10_000 })`; `onFix` keeps the latest `{lat, lng}` in a ref and, for the first fix only, sends `PUT /me/location` at once; a `setInterval(15_000)` sends the latest kept fix (nothing before the first fix). `onError` sets the message (a state set once, so a second error changes nothing). Send failures are ignored (`.catch(() => undefined)`; a 401 still ends the session through the client). The effect's cleanup calls `clearWatch` and `clearInterval`; `active` is `delivery.status === 'assigned'`, so marking delivered or leaving the page stops it. Message: "Location is off. The customer cannot see where you are." (`StatusMessage tone="warning"`). Ceiling: positions are sent only while the page is open and the phone screen is on (no background location in a web app); the customer's read shows the last one with its time.
13. **History, one page.** `GET /me/deliveries?status=delivered&pageSize=50`: `Table stack caption="Delivered deliveries"` with columns Order (a `Link` to the delivery page, `tabular-nums`), Customer, Pincode, Total (`Price`), Delivered (`when(deliveredAt)`). `total > items.length` adds the line "Showing the latest 50 of <total>.". Empty: `EmptyState` "No deliveries yet" with "Delivered orders show here.". Loading `Skeleton`, failure `ErrorBanner` "Could not load your deliveries." with retry. Ceiling: no pager; a rider past 50 deliveries sees the newest 50 (add the admin Stock pager pattern when riders ask).
14. **Time helpers copied.** `src/format.ts` holds `since(at, now)`, `useSince(at)` and `when(at)` copied from `apps/admin/src/orders.ts` at `a665845` (whole minutes, `en-IN`, `Asia/Kolkata`), plus `itemCount(n)` ("1 item" / "n items"). They are text helpers, not components, so no ui request. Ceiling: a third copy moves them to `@shopperstop/ui/format`.
15. **Phone first.** Every page is one column inside `main className="mx-auto max-w-xl px-4 py-6"`; actions are `size="lg"` (48 px) full-width buttons; the banner wraps (`flex-wrap`) so wordmark, store, name and Sign out fit 390 px. Wider screens get the same column centred. No new component is needed; every element is an `@shopperstop/ui` export or a plain heading, list or paragraph.
16. **Unit tests use a fake at the fetch boundary.** `src/fake-api.ts` (task 1) stubs `globalThis.fetch` like admin's `fake-core.ts`: routes keyed `"METHOD /api/rider/v1/<path>"` or `"METHOD /api/core/v1/<path>"` on the pathname only (handlers read the query from `request.url`), unknown routes 404 `not_found`, every `Request` recorded. Fixtures: `rider` (Arjun Rao, `...0801`, store `...0401`, `arjun@example.test`), `koramangala` (`Store`, name "Koramangala"), `readyOrder(n, over?)` (`SS-AAAA000<n>`, ids `...0a0<n>`), `delivery(over?)` (the delivery of the scenarios: `SS-AAAA0001`, Ravi Kumar, `+919800000001`, 12 80 Feet Rd / Flat 4 / 560034, Banana Robusta 1 kg x2, total 33900, `cod`, `assigned`), `json`, `apiError`, `signedInRoutes()` (`GET /api/rider/v1/me` and the store read). `src/fake-geolocation.ts` (task 4) defines `navigator.geolocation` with `watchPosition`/`clearWatch` and returns `{ fix(lat, lng), fail(code), watching(): number }`. Polling and the 15 s interval use `vi.useFakeTimers({ shouldAdvanceTime: true })` and `vi.advanceTimersByTimeAsync`, as admin's board tests do.
17. **e2e servers, without double starts.** `make e2e` runs `npm run e2e --workspaces` one workspace after another, and each Playwright run stops the servers it started before the next begins, so the rider config starts its own: core (`go run ./cmd/core` in `services/core`, url `:18080/api/core/v1/healthz`, timeout 120 s), rider (`go run ./cmd/rider` in `services/rider`, url `:18081/api/rider/v1/healthz`, timeout 120 s), `vite preview` (15175 `/rider/`), and `npx vite preview` with `cwd` `../web` (15173) and `../admin` (15174 `/admin/`), all `reuseExistingServer: !process.env.CI`, as web's config does for admin. The previews serve the `dist` folders `make e2e` built; a standalone run needs `npm run build` for the three apps first (comment in the config, as web's).
18. **e2e context.** One project `chromium`: `devices['Desktop Chrome']` with `viewport: { width: 390, height: 844 }`, `geolocation: { latitude: 12.9352, longitude: 77.6245 }` (Koramangala), `permissions: ['geolocation']`, `baseURL: 'http://localhost:15175/rider/'`. Contexts made with `browser.newContext` do not inherit `use`, so the cross-app flow passes `baseURL` (and for the rider context the geolocation options) explicitly. `globalSetup` runs `core-admin migrate`, `core-admin seed-demo --reset`, `rider-admin migrate`, `rider-admin seed-demo --reset`, in that order (D22: self-contained suite).
19. **e2e data and the sign-in budget.** Both services limit sign-ins to 10 per email per hour in memory, and a reused local server keeps the count across runs. Helpers in `e2e/helpers.ts`: `expectNoViolations`, `freshShopper` (register through core), `orderPick(request, n)` and `fillCart` copied from `apps/web/e2e/shopper.ts` at `a665845`, `addAddress`, `readyOrder(request, staff, n)` (shopper, address, cart, `POST /orders`, then `accepted`, `packing`, `ready` with a staff token), `staffToken(request)` and `riderToken(request, email)` (API sign-ins memoised per worker), `asRider(page, token)` (init script setting `shopperstop:rider-token`). The UI sign-in form is used once per rider per run (smoke uses `rider1-koramangala`, the cross-app flow `rider2-koramangala`); every other test enters with an API token. Each test that orders owns one pick index (rider flow 0, phone layout 1, cross-app flow 2); the suite's `globalSetup` reset restores stock, so web's indices 0 to 9 do not collide (web resets again in its own setup). Cards and rows are found by order number, never by position, because tests in other files may add ready orders at the same store.

Every query function throws `error.error` (the `ApiError`) on a failed answer and lets a network failure throw its `TypeError`, as admin's do; pages tell them apart with `'code' in error`.

## Test strategy

- Vitest + Testing Library through `renderApp(path)` (the real router, guard and shell on a memory history) with `fakeApi` at the fetch boundary; one test per scenario, named after it. No component of `@shopperstop/ui` is re-tested.
- Playwright against the real services (`make e2e` env): `smoke.spec.ts` (served under the prefix, both proxies, the smoke pages with axe, sign-in and sign-out in the UI, the seeded History), `deliveries.spec.ts` (ready order to delivered with the location assertion), `flow.spec.ts` (cross-app), `phone-layout.spec.ts` (scroll width and 44 px on four pages). Workers cannot run `make e2e`: task 2 type-checks and lints the specs; the manager runs the suite in task 6 and once after task 2 to see it red for the right reasons (pages missing, not config).
- `make test-web` runs the rider workspace's lint, typecheck, test and build with the others.
- Cross-app locators (admin-P3-L1 and web contract, relayed 2026-10-16): admin keeps the sign-in labels "Email", "Password", "Sign in" and names the board's next-status buttons "<action> <number>" ("Accept <number>", "Start packing <number>", "Mark ready <number>", "Mark delivered <number>"). After admin-P3-L1 the card's order number is itself a `Button size="compact"` named by the number, so every board locator is `getByRole('button', { name: 'Accept <number>', exact: true })`; never a substring or regex match on the number. The board reads all active orders in one request; cards appear as before. Web keeps "Place order (COD)", "Your order is out for delivery." and "Your order was delivered." as a contract; the flow matches them with `exact: true` too.

## Risks / Trade-offs

- Sign-in limiter: a local run with reused servers more than three times an hour can hit the 10-per-email limit (Decision 19). CI starts fresh servers. Mitigation: API tokens memoised per worker; if it bites, run with `CI=1`.
- The cross-app flow depends on web's checkout and tracking texts and admin's board button names; a change there breaks this suite. They are named in the proposal's Impact so a web or admin lane sees the dependency.
- Geolocation in headless Chromium: `watchPosition` with the granted permission and a context `geolocation` delivers the fixed position once; the e2e assertion waits up to 20 s with `expect.poll` (the first fix is sent at once, the next at 15 s).
- Parallel workers in one worktree (tasks 2 to 5) each running `make test-web` rebuild `packages/ui` at the same time; the manager may serialise the gate runs.
- Polling every 10 s and posting every 15 s cost one request each per open phone; fine at demo scale. Ceiling: server push when a notification service exists.
