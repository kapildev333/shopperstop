# Tasks

Four tasks, one worker each, in order 1 → 2 → 3 → 4 on branch `lane/web-P2-L4-checkout-orders` in `.worktrees/web-P2-L4` (each builds on the one before). The branch is rebased on `origin/main` before task 1 starts (it needs `openspec/specs/orders` from #140 only for reading). Read `design.md` first: it fixes files, interfaces, copy and test names. Where the generated types or the landed code differ from `design.md`, follow them and note it in the lane log; stop and report on a behaviour difference or any open design choice.

Rules for every task:

- Test first: commit the failing tests (`test: …`), see them fail for the reason the scenario names, then the smallest code that passes (`feat: …`). A pin (expected green on arrival) is named as one in the commit body.
- Vitest: seeded caches, no HTTP mock, no `vi.mock`. The only fake is the `send` prop (design.md, Test strategy) and the fake clock in the countdown tests.
- Compose `@shopperstop/ui` components only; colours from tokens; no change under `packages/ui`.
- A view checks its data before its error: `if (data === undefined) return error ? alert : skeleton`.
- A write is done only when its answer holds the order or address (design Decision 21); `src/api.ts` already turns every failed answer into an envelope error (web-P2-L8).
- Cart changes only through `setLine` / `clearCart` in `src/cart.ts`. Never `api.PUT('/me/cart/items')` or `api.DELETE('/me/cart')` from a page.
- e2e: inside `page.evaluate`, `page.addInitScript` and `page.waitForFunction` callbacks nothing from the Node side exists (no imported constant, helper or outer variable); pass values as the callback's argument. Every Playwright `getByRole(..., { name })` and `getByText` uses `exact: true`. In Vitest, Testing Library's `getByRole` has no `exact` option: a string `name` matches exactly by default, so pass strings, not regexes, and scope with `within(...)` where a name repeats.
- Gates, from the worktree root, Node 22.12+ (`PATH="$HOME/.local/node-v22.23.3/bin:$HOME/.local/bin:$PATH"`): `npm install` (after a rebase), `npm run build --workspace packages/ui`, `npm run lint --workspace apps/web`, `npm run typecheck --workspace apps/web`, `npm run test --workspace apps/web -- --run`, `npm run build --workspace apps/web`, `git status` clean after the build (commit the regenerated `src/routeTree.gen.ts`), `openspec validate web-checkout-orders --strict`. The e2e (`CI=1 npm run e2e --workspace apps/web` with the Makefile's `E2E_ENV` exported) runs one at a time across all areas: ask the manager for the slot; never start it unasked, never run `docker`.
- Commit as the repo's configured author, no trailers. Tick this file's boxes as they land.

Poll: `pollInterval(order)` is `10_000` while `underWay(order.status)`, `false` for `delivered`, `cancelled`, `null` (unknown order) and `undefined` (no answer yet). `orderOptions` gets `refetchInterval: (query) => pollInterval(query.state.data)`: a function of the held order's status, never a constant. `refetchIntervalInBackground` and `refetchOnWindowFocus` are left unset (no poll while the tab is hidden, one read on return); the test also asserts `orderOptions('t', id).refetchIntervalInBackground` is not `true`. Countdown and the clock: `arrival(placedAt, promisedMinutes, now)` is pure (`left = Date.parse(placedAt) + promisedMinutes * 60_000 - now`; `left <= 0` → "Running late. We are getting your order to you."; else `n = Math.ceil(left / 60_000)` → "Arriving in 1 minute" / "Arriving in N minutes"). `Countdown` keeps `now` in state from `Date.now()` and a one-second `setInterval`, cleared on unmount. No clock module, no injected clock: tests fake the clock at the process boundary with `vi.useFakeTimers({ toFake: ['Date', 'setInterval', 'clearInterval'] })` and `vi.setSystemTime(...)`, restore with `vi.useRealTimers()` in that file's `afterEach`, and never fake `setTimeout` (Testing Library's `findBy` and the router need it). The two counting tests render `<Countdown />` alone (`render`, no router), move time with `act(() => vi.advanceTimersByTime(60_000))` and assert with synchronous `getByText`. Exactly at the promised moment the text is already "Running late…". On the page: `underWay(order.status) && store && <Countdown … />` with `store` from `useStore(order.storeId)` (`src/catalog.ts`; promise is `placedAt` plus the store's current `promisedMinutes`), outside the status `StatusMessage` so a minute changing is not announced. "No countdown once finished" renders the page with a `delivered` order and a seeded store, and a `placed` order with no store seeded.

Cancel: "Cancel order" (`Button variant="ghost-danger"`) only while `canCancel(order.status)`. It opens `<Dialog title="Cancel this order?">` with the sentence "Order <number> will be cancelled and nothing will be delivered." and `<DialogFooter onCancel={close} cancelLabel="Keep order">`, so "Keep order" is the first button, then "Cancel order" (rendered only while `canCancel`). `postCancel(id)` sends `POST /orders/{id}/cancel` with the JSON body `{}` (an empty body is 400) and answers `{ order }` or `{ error }` (code `internal` when neither came), like `postOrder`. `cancelOrder(id, send = postCancel)`: with an order, `setQueryData(orderKey(token, id), order)` and invalidate `ordersKey(token)`; on `conflict`, invalidate `orderKey(token, id)`; return the result. The dialog is rendered outside the `canCancel` condition and stays open on every failure: 409 → "This order can no longer be cancelled."; anything else → "Could not cancel the order. Try again.". Opening it clears the old error. Tests use `renderInRouter(<OrderPage id={id} send={fake} />)` with the order seeded under `orderKey('t', id)`; no `vi.mock`.
